# valkey

ElastiCache Valkey replication group, shaped after `impel-gateway-sea-redis` and
`impel-identity-sea-redis`: single node group, encryption at rest and in transit, auth token,
multi-AZ with automatic failover.

## Creates

- `aws_elasticache_replication_group` (cluster mode off) with a primary and optional replicas
- KMS CMK and alias, encrypting the cache at rest and the auth token secret
- Subnet group, parameter group
- Security group accepting `:6379` from `allowed_security_group_ids`
- Auth token — generated by `random_password`, stored in Secrets Manager

## Call

```hcl
module "gateway_cache" {
  source = "../../modules/valkey"

  name                       = "impel-gateway-${var.environment}-redis"
  description                = "Gateway response and session cache."
  vpc_id                     = module.vpc.vpc_id
  subnet_ids                 = module.vpc.private_subnet_ids
  allowed_security_group_ids = [module.gateway_service.task_security_group_id]

  node_type     = "cache.t4g.micro"
  replica_count = 0
  multi_az      = false
}
```

Inject the token:

```hcl
container_secrets = {
  REDIS_PASSWORD = module.gateway_cache.auth_token_secret_reference
}
```

## Not a MemoryDB stand-in

Next's production cache is MemoryDB (`ioredis.Cluster`, ACL user `impel-next`). That contract
lives in [`memorydb`](../memorydb/). This module is cluster-mode off with a default AUTH token
and is for gateway and identity only.

## The auth token

ElastiCache has no equivalent to RDS's `manage_master_user_password`, so the token is generated by
Terraform and **does land in state**. The state bucket is CMK-encrypted and reachable only through
the plan and apply roles — treat anyone who can read it as holding this token.

Rotating means tainting `random_password.auth_token` and restarting the consuming services.

`special = false` on the generated password is not laziness: ElastiCache rejects several
punctuation classes in auth tokens, and 64 alphanumeric characters is far past the entropy that
matters.

## Notes

`allowed_security_group_ids` is fine when nothing flows back from the cache to the client. When a
service also consumes an output of this module — `kms_key_arn` for its execution role, or
`auth_token_secret_reference` for its configuration — that direction creates a dependency cycle. In
that case leave `allowed_security_group_ids` empty and grant access from the service side with the
`ecs-service` module's `data_store_ingress`.

`multi_az` requires at least one replica; a `precondition` catches that at plan time rather than
letting the API reject it minutes into an apply.

`snapshot_retention_days` defaults to `0`. For a pure cache that is correct — snapshots of a cache
mostly cost money.
